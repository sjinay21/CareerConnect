# Idempotency key: implementation step by step

## 1. Where do we implement it?

In your existing architecture:

```
Frontend
   ↓
Route
   ↓
Controller
   ↓
Service  ← Idempotency logic
   ↓
Model
   ↓
PostgreSQL
```

The service handles the business logic, while the model handles database operations. The database should enforce uniqueness to prevent two concurrent requests from processing the same key.

## 2. Step 1 — Generate the key

When the user starts a payment operation, generate a UUID in the frontend or backend.

```
import crypto from "node:crypto";

const idempotencyKey = crypto.randomUUID();
```

For example:

```
K123-abc-456
```

Generate it once for that payment operation. If the request times out and you retry it, reuse the same key. A new payment attempt should normally get a new key.

For a payment integration, the backend can generate the key when creating the checkout operation, or accept a client-generated key and validate it.

## 3. Step 2 — Store the key in PostgreSQL

One simple approach is to maintain an idempotency records table:

```
CREATE TABLE idempotency_keys (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    idempotency_key VARCHAR(255) NOT NULL,
    response JSONB,
    status VARCHAR(20) NOT NULL DEFAULT 'processing',
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (user_id, idempotency_key)
);
```

What do these columns mean?

| Column              | Purpose                                            |
| ------------------- | -------------------------------------------------- |
| `user_id`           | Identifies the user making the operation           |
| `idempotency_key`   | Identifies the logical operation                   |
| `response`          | Stores the result to return on retries             |
| `status`            | Tracks whether processing is underway or completed |
| `UNIQUE` constraint | Prevents duplicate keys for the same user          |

This is an example schema, not a requirement to add this table immediately. Some payment providers already implement idempotency for their own API operations.

## 4. Step 3 — Check the key in the service

Conceptually, your service does this:

```
async function createPayment(userId, idempotencyKey) {
  // 1. Check whether this user and key already exist.

  // 2. If completed, return the previously stored result.

  // 3. If the same operation is processing, avoid
  //    starting another one.

  // 4. If it is a new key, process the operation.

  // 5. Store the result so retries can reuse it.
}
```

This is the logic outline, not production-ready code yet. The actual implementation must handle concurrent requests, failed operations, and database transactions correctly.

## 5. Step 4 — Handle repeated requests

Suppose the user submits the same request twice with key `K123`.

| Request             | Key    | Expected behavior                                            |
| ------------------- | ------ | ------------------------------------------------------------ |
| First request       | `K123` | Starts the operation                                         |
| Retry               | `K123` | Returns the existing result or reports that it is processing |
| Another retry       | `K123` | Does not create a duplicate operation                        |
| New payment attempt | `K456` | Can start a separate operation                               |

The key must also be associated with the original request's parameters. Reusing the same key with a different plan or amount should be rejected, not treated as the original operation.

## 6. Step 5 — Integrate with a payment provider

When using Stripe, Razorpay, or Paddle, there is an additional distinction:

- Your backend's idempotency: prevents duplicate processing in your own application.
- Provider idempotency: prevents duplicate provider-side operations where the provider supports it.

For example, when your backend creates a Stripe payment operation, it can send an idempotency key to Stripe as well. Your backend must still verify payment outcomes and update the subscription safely.

API: `POST /payments`

### Phase 4 — Transaction-safe completion

- Update the payment status.
- Activate the subscription only after simulated payment success.
- Calculate the start and expiry dates.
- Commit related database changes together.
- Roll back unexpected database failures.

Learn: `BEGIN`, `COMMIT`, `ROLLBACK`, atomicity, and error recovery.

### Phase 5 — Idempotency and concurrency

- Handle repeated requests using the same key.
- Return the existing result for completed requests.
- Reject reuse of a key with different request data.
- Prevent two simultaneous requests from activating duplicate purchases.

Learn: unique constraints, race conditions, locking where needed, and safe retries.

### Phase 6 — Subscription access and lifecycle

APIs

- `GET /subscriptions/me` — retrieve the logged-in user's subscription.
- `POST subscriptions/:id/cancel` — cancel according to the agreed cancellation policy.
- Check subscription status before granting premium access.
- Handle expiry and cancelled subscriptions correctly.

Learn: authorization middleware, ownership validation, and lifecycle rules.

### Phase 7 — Expiry cron job

- Find subscriptions whose expiry time has passed.
- Update active subscriptions to `expired`.
- Make the job safe to rerun.
- Handle date boundaries and database errors.

Learn: scheduled jobs, time handling, idempotent job execution, and failure recovery.

### Phase 8 — Testing and reliability

Test:

- Successful and failed payments.
- Duplicate requests and concurrent purchases.
- Database errors and transaction rollback.
- Expired plans and inactive plans.
- Subscription expiry and authorization.

Learn: integration testing, edge cases, audit logging, and recovery strategies.
